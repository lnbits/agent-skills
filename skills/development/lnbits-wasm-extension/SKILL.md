# LNbits WASM Extension Builder

Build the smallest complete product allowed by the selected LNbits WASM runtime. Do not add Python extension code, modify LNbits core, or weaken the iframe/storage boundary unless the user explicitly requests core work.

## Resolve the Runtime Before Designing

Never guess what “current LNbits” means.

1. Use the LNbits checkout, version, commit, container, or repository ref supplied by the user.
2. Otherwise, search the workspace and common sibling directories for an LNbits checkout containing `lnbits/core/wasm_ext/wasm/config.py`.
3. If no local checkout or running target is available, stop and ask for its location. Do not fetch an unrelated runtime.
4. Record the exact commit SHA or release version used as the target.
5. If `lnbits/core/wasm_ext` is absent, stop: that target does not expose this WASM extension contract.

Read [references/runtime-discovery.md](references/runtime-discovery.md) completely before creating files. Run its inspector and read the listed source files before selecting permissions, storage calls, or bridge actions. Runtime source wins over this skill when the contract changes.

## Convert the Request Into a Contract

Read the whole request. Write a compact capability matrix before implementation:

| Product action | Auth context | Export | HTTP/event trigger | Host calls | Permission | Stored/public data |
|---|---|---|---|---|---|---|

Classify each action as `authenticated`, `public`, or `event`. Verify every intended host call supports that context. Identify trust boundaries, ownership, invariants, destructive actions, idempotency keys, data that must never become public, expected cardinality/concurrency, aggregate-consistency needs, and the runtime budgets each flow must fit.

If the runtime cannot implement a requirement, name the unavailable host capability and ask before changing the product. Do not invent undeclared host calls, expose private fields, denormalize authoritative data, add a core patch, or substitute a materially different feature silently.

## Work Order

1. Resolve and inspect the exact runtime.
2. Produce the capability matrix and storage model.
3. Resolve infeasible or ambiguous security/payment requirements.
4. Create `config.json`, WIT world, source, storage schema/migrations, API documentation, UI entrypoints, browser bridge client, tests, and build files as needed.
5. Implement and test pure domain rules first.
6. Add host adapters and thin JSON exports.
7. Implement the iframe UI against declared bridge routes only; test each rendered action before moving on.
8. Build `wasm/module.wasm`; never hand-edit generated bytes.
9. Reload or restart through the selected runtime's component-registration lifecycle, then validate contract synchronization, permissions, security, SQLite/PostgreSQL behavior, browser CSP behavior, and real installation.
10. Package the exact tested tree; compare the archive's component hash with `wasm/module.wasm`.

Read the references required by the requested features:

- Always: [references/backend-contract.md](references/backend-contract.md) and [references/verification.md](references/verification.md).
- Any UI: [references/frontend.md](references/frontend.md) and [references/frontend-recipes.md](references/frontend-recipes.md). Use the standalone skeletons; do not copy another extension.
- Incoming invoices, outgoing payments, or paid events: [references/payments-events.md](references/payments-events.md).

Read the matching capability section before using public storage, WebSockets, or background wallet permissions. Do not infer an SDK method or browser-bridge action from a permission name.

## Required Product Repository

Use this baseline; omit files for capabilities the product does not need:

```text
<extension-id>/
  config.json
  wasm/
    lnbits-extension.wit
    module.wasm                 # generated install artifact
    openapi.json                # optional API operation/schema metadata
  storage/                      # only when persistence is needed
    schema.json
    migrations/
      0001_initial.json
  ui/                           # only when UI is needed
    admin.html
    public.html
  static/                       # only when UI is needed
    admin.js
    public.js
    app.css
    lnbits-extension-sdk.js
    assets/
      icon.png                   # required by the LNbits extension list
  dev/
    package.json or equivalent language build files
    src/
    test/
  manifest.json                 # only for repository/marketplace discovery
```

`config.json` is the install/runtime contract. `manifest.json` is repository-listing metadata, not the WASM runtime config; add it only for a distribution channel that consumes it. Keep build metadata under `dev/`.

## Synchronization Invariant

For every callable feature, keep all applicable declarations identical:

1. `config.json` `wasm.exports[*]` name and visibility.
2. WIT world export name and signature.
3. Source-language exported function.
4. `api_routes[*].export` or `events.onInvoicePaid` target.
5. Frontend SDK method and route, when invoked from UI.
6. `wasm/openapi.json` route key, parameters, request body, and response envelope, when API metadata is shipped.

Use `func(request-json: string) -> string` for HTTP exports. Use the event parameter name only as source-language documentation; the WIT type remains a string. Return exactly one envelope shape:

```json
{"ok":true,"data":{}}
```

or:

```json
{"ok":false,"error":"Safe, actionable message"}
```

Accept JSON objects only. Validate type, length, range, enum membership, relationships, authorization assumptions, and state transitions at the export boundary. Never return raw host exceptions or secrets.

## Security Rules

- Request only permissions used by reachable code.
- Treat public request bodies, route/query parameters, event payloads, external responses, and cross-extension responses as untrusted.
- Let LNbits enforce owner scope; never read, write, filter, index, or return its reserved owner field.
- Never accept a user ID, owner ID, API key, or private wallet ID merely because a caller supplied one.
- Keep wallet IDs, payment hashes, preimages, access tokens, private rows, and operational metadata out of public responses unless the product explicitly and safely requires a field.
- Render user-controlled text with `textContent` or escaped framework bindings, never `innerHTML`.
- Use only static file types served by the selected runtime. Do not add or reference SVG unless that runtime explicitly serves it; prefer PNG, WebP, JPEG, canvas, or plain HTML/CSS.
- Do not use direct iframe cookies, parent globals, parent DOM/components, or unrestricted `fetch` as a bridge bypass.
- Make event processing idempotent before applying irreversible or counted effects.
- Confirm ownership and current state again immediately before destructive or monetary actions.

## Implementation Rules

- Keep domain logic independent of generated host bindings so it can be tested with in-memory fakes.
- Keep each export thin: parse → validate → call domain/host logic → envelope.
- Use host-provided random IDs and time where deterministic tests can substitute them.
- Use the generated TypeScript host contract when JavaScript/TypeScript is selected; do not recreate request/response types from memory.
- Use only WIT interfaces actually needed by the component, but ensure their records exactly match the target runtime.
- Keep old released migrations immutable; add ordered migrations and update `schema.json` together.
- Avoid dependencies and framework build pipelines unless they remove more risk than they add.

## UI Rules

The UI runs in a sandboxed iframe with a strict CSP and separate global scope. It may load only assets explicitly proxied by the selected runtime and extension-owned static files.

Choose one ownership model per page:

- Static HTML owns the DOM: use `type="button"` and `addEventListener`.
- Vue owns the DOM: use Quasar components and Vue `onClick`; do not also attach DOM listeners.

For Vue/Quasar, mount an iframe-local app and use CSP-safe render functions or precompiled templates. Never use runtime template compilation (`template:`, DOM templates, `new Function`, or `eval`).

Load an approved LNbits-proxied stylesheet on every UI route. When Quasar is selected, prefer its components and utility classes for layout, spacing, controls, cards, dialogs, tables, typography, colors, and responsive behavior.

Keep extension CSS only for product-specific visuals or behavior that Quasar does not provide. The iframe does not inherit parent styles, so use only runtime-proxied assets; never assume the parent page's loaded CSS crosses the iframe boundary.

Follow the selected runtime's established WASM theme convention; do not mix theme-neutral and forced-dark components on one page. Parent-theme changes do not cross the iframe unless the runtime provides a theme bridge.

Use the parent bridge for extension API calls, route context, LNbits-native notifications, QR scanning, navigation, and payment subscriptions. Do not use `<form>`, submit controls, or native form workflows: the iframe has no `allow-forms` sandbox capability and CSP sets `form-action 'none'`. Bind `type="button"` controls explicitly, disable actions while invalid/loading, re-enable them after recoverable failures, and verify the rendered click path—not merely the called method—in a runtime test.

Use framework spacing/layout utilities before adding CSS. Every toggled detail card or dialog needs an explicit close button and state-clearing handler.

The component JavaScript runtime is not Node or a browser. Feature-detect optional built-ins such as `String.prototype.normalize`; do not assume `Intl`, DOM APIs, `fetch`, Node modules, or Web Crypto exist in component code. A Node unit test is insufficient: load or invoke the rebuilt component against the real WIT/runtime.

## Definition of Done

Do not claim completion until:

- the exact target runtime/ref is recorded;
- config, WIT, source, route/event, and frontend declarations agree;
- every permission maps to an actual host call and every public policy is minimal;
- schemas and migrations agree and work on both SQLite and PostgreSQL when available;
- focused domain, export, replay, ownership, and public-data tests pass;
- frontend code runs under a CSP that forbids string code generation and direct network access;
- the component rebuild succeeds and is a valid WebAssembly Component;
- authenticated and signed-out flows work in the target LNbits instance;
- every primary button, close action, dialog, and navigation action is exercised through the rendered UI;
- restart persistence and relevant payment/event flows are manually verified; and
- the release archive layout matches the selected runtime's installer, contains the configured module, and preserves the exact tested component bytes.

## Handoff

Report the target LNbits commit/version, extension ID/version, capabilities, requested permissions/policies, files created, exact build/test commands and results, install/manual-test steps, and any verified runtime limitation. State what was not tested. Do not call a source-only tree installable when `module.wasm` was not rebuilt.
